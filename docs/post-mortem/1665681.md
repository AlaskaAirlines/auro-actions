# AB#1665681

## Executive Summary

Published Auro packages ship a component metadata file (`custom-elements.json`) that tools use to describe the package's components. Until now that file did not say which package build it belonged to, so a consumer or tool could not tell which package and version a given copy of the file came from. This change makes the PR build process stamp the file with the package name and version (for example `@aurodesignsystem/auro-button-dev@0.0.0-pr123.0`) just before the build is published. The same stamping now happens on regular releases, using the version the release process is about to publish, so no setup is needed in individual component repositories.

## The Problem

The metadata file included in every published Auro package was anonymous. Nothing in it identified the package or version it described. Anyone looking at a copy of the file, or any tooling that consumed it, had to infer where it came from. Pull request builds, which publish temporary preview versions, made this more likely to cause confusion because many near-identical versions exist at once.

## Root Cause

Nothing in the shared workflows wrote package identity into `custom-elements.json`. In `.github/workflows/pull-request.yml`, the `release` job runs `auro pr-release`, which only rewrites `package.json` with a PR-specific version, then runs `npm publish`. The `custom-elements.json` produced by the earlier build job (restored from cache via `cache-dirs`) was published as generated. For releases on push, `.github/workflows/release.yml` delegates entirely to `npx semantic-release`, which calculates the version internally during its own run, so no workflow step has the version available before publishing.

## The Fix

- `.github/workflows/pull-request.yml`: added an "Add package to custom-elements.json" step after the existing "Read package.json" step and before "Publish to NPM". It takes the package name and version from that step's outputs (passed through `env:` rather than interpolated into the script), sets `manifest.package = "<name>@<version>"` on the parsed `custom-elements.json`, and writes it back. If the file is missing it logs a warning and skips instead of failing the publish.
- `.github/workflows/release.yml`: added an "Add package to custom-elements.json" step before "Release". It runs `npx semantic-release --dry-run` (with the same `GITHUB_TOKEN` and `NPM_TOKEN`), extracts the version from the "The next release version is X" line, and writes `<name>@<version>` into `custom-elements.json`, with the name read from `package.json`. If the dry run fails, the step fails. If it reports no release, or the file is missing, the step logs a notice or warning and skips.
- `README.md`: added a "`custom-elements.json` package field" section describing how both workflows set the field and the dependency on semantic-release's log wording.

## Why This Works

- In the PR workflow, `auro pr-release` has already written the final PR version to `package.json` by the time the new step runs, and `npm publish` has not run yet, so the stamped value matches what is about to be published. The restored `custom-elements.json` is in the working directory because it is part of the cached build output.
- For releases, the dry run uses the same commit analysis as the real run, so the version it reports is the one the real run will compute, provided no new commit lands in between. Dry-run mode does not modify `package.json` or publish anything, so running it first has no side effects on the release.
- Values reach the Node script through environment variables, not string interpolation into the shell command, which avoids script-injection issues in the workflow.

## Outcome

PR preview builds and regular releases will publish with a metadata file that states which package and version it describes. Release stamping relies on the wording of semantic-release's dry-run output, so it needs checking after semantic-release upgrades.

## Learnings

- semantic-release only knows the next version during its own run, so a plain workflow step before `npx semantic-release` cannot see it from `package.json`. `--dry-run` is the way to learn it from a shared workflow.
- Parsing the dry-run output ties the workflow to semantic-release's log wording; the match is anchored on "The next release version is" plus a semver-shaped token, and the step skips quietly when no version is found.
- The dry run runs plugin verification twice and could report a different version than the real run if a commit lands in between; both are accepted trade-offs of keeping the change in the shared workflow.
- Pass workflow values to scripts through `env:` and read them from `process.env`; do not interpolate step outputs into the script body.
- Doing the work inside semantic-release (an `@semantic-release/exec` plugin listed after `@semantic-release/npm`) is more robust, but lives in each consumer's config and needs a coordinated rollout across repos.

## Iterations That Didn't Work

- Documenting an `@semantic-release/exec` plugin (after `@semantic-release/npm`, `prepareCmd` running a script) for each consuming repo to adopt. It was technically more robust, but it left releases unstamped until every repo was updated, so it was replaced by the dry-run step in the shared `release.yml`.
