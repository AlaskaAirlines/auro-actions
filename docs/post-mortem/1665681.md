# AB#1665681

## Executive Summary

Published Auro packages ship a component metadata file (`custom-elements.json`) that tools use to describe the package's components. Until now that file did not say which package build it belonged to, so a consumer or tool could not tell which package and version a given copy of the file came from. This change makes the PR build process stamp the file with the package name and version (for example `@aurodesignsystem/auro-button-dev@0.0.0-pr123.0`) just before the build is published. Stamping the file automatically on regular releases is not done by this change; it needs a small, one-time setup in each Auro component repository, which is documented in this repo's README.

## The Problem

The metadata file included in every published Auro package was anonymous. Nothing in it identified the package or version it described. Anyone looking at a copy of the file, or any tooling that consumed it, had to infer where it came from. Pull request builds, which publish temporary preview versions, made this more likely to cause confusion because many near-identical versions exist at once.

## Root Cause

Nothing in the shared workflows wrote package identity into `custom-elements.json`. In `.github/workflows/pull-request.yml`, the `release` job runs `auro pr-release`, which only rewrites `package.json` with a PR-specific version, then runs `npm publish`. The `custom-elements.json` produced by the earlier build job (restored from cache via `cache-dirs`) was published as generated. For releases on push, `.github/workflows/release.yml` delegates entirely to `npx semantic-release`, which calculates the version internally during its own run, so no workflow step has the version available before publishing.

## The Fix

- `.github/workflows/pull-request.yml`: added an "Add package to custom-elements.json" step after the existing "Read package.json" step and before "Publish to NPM". It takes the package name and version from that step's outputs (passed through `env:` rather than interpolated into the script), sets `manifest.package = "<name>@<version>"` on the parsed `custom-elements.json`, and writes it back. If the file is missing it logs a warning and skips instead of failing the publish.
- `README.md`: added a "`custom-elements.json` package field" section explaining that release-on-push cannot be handled in the shared workflow. It tells consuming repos to add `@semantic-release/exec` after `@semantic-release/npm` in their semantic-release plugins, with a `prepareCmd` that runs a short script reading `name` and `version` from `package.json` and writing the `package` field.
- `.github/workflows/release.yml` is intentionally unchanged.

## Why This Works

- In the PR workflow, `auro pr-release` has already written the final PR version to `package.json` by the time the new step runs, and `npm publish` has not run yet, so the stamped value matches what is about to be published. The restored `custom-elements.json` is in the working directory because it is part of the cached build output.
- For releases, `@semantic-release/npm` writes the new release version into `package.json` during its own prepare step. Because plugin prepare steps run in the order listed, an exec plugin placed after it sees the real version and can read it the same way the name is read, with no prediction needed. That is why the README stresses the plugin order.
- Values reach the Node script through environment variables, not string interpolation into the shell command, which avoids script-injection issues in the workflow.

## Outcome

PR preview builds will publish with a metadata file that states exactly which package and version it describes. Regular releases are not covered yet: each consuming repo needs to adopt the documented semantic-release configuration before its releases carry the same field, so until then those published releases will still lack it.

## Learnings

- semantic-release only knows the next version during its own run, so a plain workflow step before `npx semantic-release` cannot see it from `package.json`.
- `@semantic-release/npm` writes the version into `package.json` in its prepare step, and plugin order determines what later plugins see. Put `@semantic-release/exec` after it when the script reads `package.json`.
- Doing the work inside semantic-release (exec plugin) is more robust than predicting the version from the output of a `--dry-run`: it does not depend on log wording, avoids running plugin verification twice, and cannot drift if new commits land between the dry run and the real run.
- Pass workflow values to scripts through `env:` and read them from `process.env`; do not interpolate step outputs into the script body.
- Shared reusable workflows cannot change behavior that lives in each consumer's semantic-release configuration, so some changes require a coordinated rollout across repos.

## Iterations That Didn't Work

- A step in `release.yml` ran `npx semantic-release --dry-run`, parsed "The next release version is X" from the output, and combined it with the `package.json` name. It was removed because it depends on semantic-release's log text, runs the plugin checks twice, and could report a different version than the real run if another commit landed in between. It was replaced by the `@semantic-release/exec` approach documented in the README.
